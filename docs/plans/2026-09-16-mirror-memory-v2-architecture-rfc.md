# RFC 0001 — Mirror Memory v2 Architecture

- 状态：Draft，供评审；文中的“必须”是拟议契约，不代表已有实现。
- 日期：2026-09-16。
- 更新：2026-09-17；确认旧版无需兼容、embedding 可选、对话型 toC 消费者、PostgreSQL、信任制用量护栏和业务授权来源。
- 目标：以最小可交付范围，建立可投入实际业务的长期记忆内核。
- 存放说明：本稿暂存于 Psych 工作区，后续迁入 mirror-memory 仓库；本次不修改运行代码。
- “v2”是架构代号；正式包版本在发布前确定，不预设直接发布 2.0。旧 Mirror 退役，新版从全新 API 与 schema 开始，无旧版兼容义务。

## 1. 决策摘要

Mirror 为业务应用提供有来源、可修正、可控制生命周期的长期记忆。它负责接收经历、形成记忆、维护当前理解、按授权和预算召回，并解释这些结果如何产生。

首版采用 Python 模块化单体、PostgreSQL 权威存储、数据库事务任务表和独立 worker。先实现一个偏好记忆业务闭环，再加入模型抽取和按需检索；embedding 不作为基础依赖。不 fork 某个完整记忆平台，也不把五个开源项目组合成运行依赖。

对外提供小而稳定的用例接口；内部将证据、推断、当前视图和本次召回分开。领域逻辑通过受约束的代码接口扩展。Psych 继续保留现有实现，未来是否迁移由影子评测决定。

已确认面向对话型 Agent、与用户持续亲密交互的 toC Agent 产品；首个试点为 Psych 内部对话测试，验证成功后扩展到笔润智谈等产品。以 PostgreSQL 持久化，从小范围使用起步。经济参数通过测试寻找质量约束下的成本效率工作点，形成可调整的默认信任制护栏。业务负责身份和用户授权，Mirror 与可信业务后端握手、消费授权状态并执行边界。容量测量值、部署位置、模型数据去向及分层保留期限在相应阶段补齐。

## 2. 服务对象、首个场景与范围

首批消费者是对话型 Agent，以及与用户持续亲密交互的 toC Agent 产品。直接使用 SDK 的是这些产品的业务开发者，间接使用者是需要被正确记住、能够纠正和删除记忆的终端用户。业务方应能调用 observe、recall、correct、forget 等接口，而无需理解内部任务与索引实现。

首个验证闭环在 Psych 的内部测试环境进行：用户说明技术问题需要详细回答，下一次技术讨论能正确使用；临时要求简洁不覆盖长期偏好；用户更改偏好后旧偏好停止影响回答；用户删除后不能被任务重试恢复。先用合成/脚本化对话和已明确同意的内部测试者数据，不默认复用生产历史。先旁路比较记忆结果，再在独立测试会话中接入回复；内部测试成功不自动授权替换 Psych 生产记忆。

后续“迁移至笔润智谈”解释为框架能力的接入推广，不是将 Psych 用户的心理相关记忆迁往另一产品。默认保持应用隔离，不推定跨产品共享授权。Psych 是第一消费者，第二产品接入是检验通用性的必要证据；核心契约不得因此依赖 Psych 专有概念。

偏好用例用于验证基础设施，不代表已经覆盖亲密对话产品的记忆需求。M2 的验收样例还须包含阶段性计划和历史经历：区分“过去发生过”与“现在仍成立”，保留人物与事件的归属，不把 assistant 推测归为用户事实。仅通过偏好测试时，只能宣称偏好场景可用。通用层不据此增加人格诊断或关系亲密度评分。

### 首版做什么

- 接收带身份、来源、时间与幂等键的文本事件。
- 形成有证据引用的原子记忆和版本化当前视图。
- 支持显式纠正、同作用域替换、简单冲突保留和休眠。
- 按业务用途、授权、状态、相关性与 token 预算召回。
- 提供形成与召回解释、处理进度、导出及删除回执。
- 支持可重试后台处理、故障恢复、数据迁移、可重建索引。

### 首版不做什么

- 完整 Agent 平台、聊天 UI、身份账户系统、共享团队知识平台。
- 心理诊断、人格推断、危机处理或心理学 K1/K2/K3 内核。
- 多模态、跨用户学习、跨租户知识融合、自主修改系统指令。
- 图数据库、多数据库兼容、微服务拆分、通用插件市场。
- 学习型半衰期、自动生成 ontology、任意多跳图推理。
- 全量对话归档的强制替代品，或不经授权的原文长期保存。

未来扩展必须由业务收益、验收用例和现有能力不足共同证明。

### 产品完成度：可靠、精巧、易用

目前 RFC 是工程设计草案，尚未通过真实接入证明产品完成度。以“苹果”类比所追求的体验，应落实为下列验收要求，不作为品牌背书或质量结论。

- 一条推荐接入路径：首版以 Python SDK 为主入口，提供固定依赖版本的本地启动示例、环境检查和 basic-preference 示例。HTTP 层在出现独立服务消费者时再交付，不同时维护两套首发体验。
- 渐进披露：默认用户只需理解业务身份、用途、输入和返回结果；Evidence、Atom、租约、排序权重属于内部或诊断视图。可信身份可由已绑定上下文提供，不能为了减少参数而省略身份校验。
- 完整操作体验：同一示例覆盖记住、等待可用、跨会话召回、纠正、解释和删除。处理中的结果不能显示为“没有记忆”，阻断使用不能显示为“已彻底删除”。
- 一致且有帮助的失败响应：错误包含稳定错误码、是否可重试和下一步建议；不暴露数据库异常、模型原始响应或内部堆栈。
- 有默认行为：提供一套带版本的偏好形成、冲突和固定衰减策略；采用者无须先理解或调整半衰期、向量权重和 worker 参数才能完成示例。
- 可验证的接入质量：M2 邀请一名未参与内核开发的开发者，仅凭文档完成完整示例；记录耗时、卡点和人工协助。M3 前消除必须口头补充的关键步骤，并完成断网/模型失败/worker 重启后的恢复演练。

首版不以配置项或接口数量证明通用性。至少第二个真实领域的接入证明抽象合适后，再扩展公共插件契约。

## 3. 核心不变量

| 编号 | 必须保持的行为 |
| --- | --- |
| I1 | 租户、主体和应用边界由可信身份上下文确定；请求中的 user_id 不是授权凭据。 |
| I2 | 每条可使用的派生记忆都有有效来源链；来源存在不意味着推断正确。 |
| I3 | 原文与已生成语义不静默覆盖；纠正产生新修订。删除、脱敏和到期清除优先于历史保留。 |
| I4 | 写入、模型外发、结果提交、召回分别检查当前策略；领域模块只能收紧权限。 |
| I5 | 业务写入与任务入队在同一数据库事务完成；重复投递不重复形成或强化记忆。 |
| I6 | 索引和缓存是派生数据；不能独立授予权限，也不能成为唯一事实来源。 |
| I7 | 未批准、已替换、已删除及默认休眠内容不进入普通召回；历史查询需要显式模式与授权。 |
| I8 | 模型输出经过结构与业务校验；缺失证据、越界引用或未知语义不得静默变为有效记忆。 |
| I9 | 每次返回记忆都有可追踪回执；外部应用是否真正注入由应用报告，Mirror 不伪称已经使用。 |
| I10 | 模型、Prompt、领域规则和数据结构的版本变化可区分；索引重建不触发重新推断。 |

## 4. 概念与数据所有权

| 概念 | 含义及最小责任 |
| --- | --- |
| Scope | tenant、subject、app 是隔离根；agent/session 是可选限制维度；purpose 是授权用途。缺少隔离根拒绝操作，空 session 不隐式放开其他边界。 |
| Evidence | 来源事件：source_event_id、来源角色、发生时间、记录时间、内容或受控引用、保留类别。用户陈述、assistant 输出、外部工具结果需区分。 |
| Atom | 单条抽取断言：类型、语义、情境、适用时间、evidence_refs、generation_run。显式陈述和模型推断分别标记。 |
| Relation | 断言间的支持、冲突、细化、替换关系及依据；首版使用关系表。 |
| ViewRevision | 对一组断言的当前理解，包含输入引用、规则版本、修订号和可用状态；批准版本的切换是原子操作。 |
| LifecycleEvent | 某条记忆被确认、休眠、激活、替换的变化及原因；不把所有概念塞进一个状态枚举。 |
| PolicyDecision | 当时的授权、用途、敏感规则与策略版本；历史决策不可替代当前授权。 |
| GenerationRun | 提取或整合的输入输出引用、模型/Prompt/规则版本、状态、耗时、用量和错误分类。 |
| RecallReceipt | 本次查询模式、返回 ID/修订、选择理由、策略版本、预算与降级状态。默认不复制敏感原文。 |
| Job / DeletionReceipt | 后台任务的状态与租约；删除的阻断、清理和验证进度。 |

这些是逻辑对象，不要求一对象一表或一对象一个包。数据表设计须由事务和查询需求推导。

Evidence 记录的是“谁在何时说了什么”，不保证其内容是世界真相。Atom 是可质疑的断言；View 是可修正的理解。业务最终回复和即时对话历史归调用方所有。

首版支持受保留策略约束的文本存储；外部引用只保留接口边界。引用模式若无法重新取得原文，必须报告不可重放，不能声称可完整重建。来源被删除或到期后，其派生内容默认失效并进入清理；首版不允许无来源孤立保留。

### 4.1 业务与 Mirror 的授权契约

业务拥有账户身份、用户同意界面、授权授予/撤销及其法律或产品依据。Mirror 不采集同意、不判断用户是否已付费，也不维护另一套账户系统。它从可信业务后端或注入的授权接口取得当前操作的授权结果。

用户要求采用与业务 Agent 握手的方式。工程上，握手对象必须是业务的可信授权模块，而非模型生成的“用户已同意”文字。业务负责确认并记录用户授权，握手绑定调用方、Scope、用途、允许操作和版本；到期续验、撤销通知及确认属于同一协议。握手成功不授予永久权限，内部测试同样适用。

业务仍须提供不透明的 tenant/app/subject 标识以隔离数据；Mirror 无需姓名、手机号、登录凭据或同意原文。所谓“仅获取授权状态”不能实现为与用户、用途、操作和时间无关的全局 boolean。逻辑上的最小结果是：绑定 Scope、purpose、operation 的 allow/deny、单调递增授权版本，以及可验证的新鲜度（例如有效期）。精确字段由 M1 接口设计确定。

首版授权入口为可信后端注入的 AuthorizationProvider；不接受终端客户端自报的 allow=true。Mirror 仅保存执行、审计和撤销阻断所需的最小状态/版本，业务仍是授权事实来源。读取、存储、外发处理的权限不能相互推导；未知、过期或无法取得的授权结果拒绝对应操作。

为支持异步工作，业务变更授权后须同步或推送新版本到 Mirror 的执行屏障；worker 在外发前及结果提交时使用当前屏障复核。集成协议必须定义交付、重试与确认，重复通知幂等，旧版本不得覆盖新版本。Mirror 的“即时阻断”从收到并提交撤销版本后生效；业务侧变更到该确认之间的传播延迟必须测量和说明。若只有一次性入队授权、没有可更新状态，不能承诺撤销后停止后台任务。

授权与保留期限是两件事。业务/部署方选择原文、派生数据、审计和备份的保留规则，Mirror 执行这些规则及删除接口。当前授权可用不等于永久保留许可；具体期限仍待上线前确认。

“参考业界主流”作为制定默认 profile 的依据，不作为一个已经确定的天数。至少分别设置：测试原文与派生记忆的到期日、无内容运行日志的窗口、删除任务完成时限、备份轮换期限。Psych 内部试点建议使用有明确结束日的测试批次，批次结束且评审完成后按预设期限清理；长期稳定性先用模拟时钟测试。真实测试数据入库前必须有显式 profile，不能用缺省值表示无限保留。正式产品的长期记忆期限另行根据用途制定。

参考：[ChatGPT Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq)区分聊天与记忆，并对旧版已删除记忆日志描述最长 30 天留存；这不是所有记忆的默认 TTL。[Mem0 删除文档](https://docs.mem0.ai/core-concepts/memory-operations/delete)强调按范围删除与验证，也不能据此推出统一期限。来源到期导致派生记忆清理的本 RFC 规则继续有效；若未来希望摘要比原文保留更久，必须另行定义最小证据及授权规则，不能静默留下无来源记忆。

## 5. 架构与依赖方向

```text
业务应用 / 可选 HTTP 接入
              ↓
Application：用例、授权、事务、并发控制
        ↙         ↓           ↘
Domain contracts  Core       Repository / Model / Search ports
        ↑                      ↑
basic domain               PostgreSQL / LLM adapters

observe → PostgreSQL〔Evidence + Job，同一事务〕
                            ↓
                          Worker
                            ↓
                 Atom / Relation / ViewRevision
                            ↓
                   可重建的召回投影
                            ↓
recall → 检索 → 当前策略与状态复核 → 预算裁剪 → Receipt
```

单一 Python 分发包内组织 core、application、domains、adapters、runtime、api 模块；首版不拆成多个独立发布包。Core 不依赖 Web、数据库或模型 SDK。Application 负责调用顺序，adapter 实现外部能力。Domain 返回候选与决策，不能取得任意数据库连接或自行写入。

领域扩展首版只支持仓库内可信 Python 代码，接口含抽取、整合、生命周期规则与语义校验。统一内核负责授权、证据检查、持久化、幂等和回执。检索相关性可由领域调整，但不能取消安全过滤。

Mirror 返回结构化记忆项及可选的有长度限制的文本呈现；业务负责组装最终 Prompt。记忆文本始终是数据，不提升为 system 指令，用户原文中的“忽略规则”等内容不能变成运行指令。

## 6. 关键流程和一致性

### 6.1 接收与形成

1. 将调用身份映射为可信 Scope，验证用途、存储授权、消息角色和大小限制。
2. 在一个事务中保存 Evidence 与任务。以隔离根和 source_event_id 保证幂等；同键不同内容返回冲突。
3. 返回 accepted receipt 和处理进度标识。accepted 仅意味着可靠接收，不承诺新记忆已可召回。
4. Worker 领取任务，复核授权后执行规则或模型提取；模型调用不占用长数据库事务。
5. 校验候选与证据引用，在短事务中复核授权版本和删除标记，保存 Atom、Run、View 与后续投影任务。
6. 使用 subject/app/domain 级视图修订比较更新；冲突后读取新修订重算，禁止旧 worker 覆盖新理解。

任务采用至少一次执行。结果通过 Evidence、操作版本与输入集合的去重键实现幂等；不承诺模型调用恰好一次。超时重试可能产生额外供应商费用，需计量并设置上限。

PostgreSQL 任务表先同时承担事务入队和持久工作队列；字段含 lease_until、attempt、next_attempt_at、error_code。领取使用数据库并发机制，具有有界重试、过期租约恢复、失败任务重放和队列积压限制。无需先引入 Redis/Kafka。

### 6.2 召回与新鲜度

recall 接收 query、Scope、purpose、mode=current/history、预算和 deadline。隔离及有效性过滤先进入数据库查询，返回前再次复核；按当前授权获取实际内容，不能只依赖向量索引的 metadata。

响应必须区分 ok、empty、pending、degraded、denied、timeout。包含投影水位或修订和 receipt；empty 不代表系统从未接收相关信息。业务需要 read-your-writes 时可等待某个接收回执到达 ready，等待必须有 deadline。

没有匹配或检索超时可以返回空上下文，让业务继续；策略不可用时拒绝该记忆操作。不能通过返回未经校验的旧缓存降级。缓存若启用，键必须包含 Scope、purpose、策略版本和投影版本。

召回无须调用生成模型。预算包含返回条数和 token，使用指定 tokenizer 或保守估算并保留余量；最终 Prompt 的总预算由业务控制。

### 6.3 纠正、撤销与删除

correct 记录有来源的用户纠正，先同步阻断已知错误版本继续被当前召回使用，再安排重算。先比较情境：技术问题简洁与情绪支持详细可以共存，不能仅凭文本相反就做替换。

撤销写入当前授权版本/epoch；之后开始的操作必须拒绝，尚未提交的任务在提交点检查 epoch 并废弃越权结果。已经外发给模型或已经交付给调用方的内容无法追回，应明确此边界。召回的最后授权检查定义返回操作的线性化点，并测试与撤销的并发交错。

forget 先建立作用域或来源删除屏障，使当前读写立即不可用，再异步清理 Evidence、Atom、关系、视图、embedding、缓存以及可能包含内容的审计数据。回执区分 blocked、purging、verified、failed；必须验证后才标为完成。

删除事件防止旧任务重试重新入库；重新授权不能自动复活旧数据。删除所需的最小标记也受访问和保留管理，不保留原文或可枚举内容指纹作为“永久审计”。备份恢复前重放删除记录；备份保留、第三方留存和已导出副本另列边界，不能用在线删除回执承诺全部抹除。

### 6.4 模型与索引故障

| 故障 | 规定行为 |
| --- | --- |
| 模型超时、限流或输出非法 | 有界重试或隔离失败；Evidence 保持处理状态，不发布残缺视图。 |
| Worker 在提交前崩溃 | 租约到期后重试；提交后崩溃依靠去重键防止重复结果。 |
| 投影更新失败 | 保留主数据，报告投影滞后，重试重建；旧索引不能越过当前状态过滤。 |
| Embedding 模型更换 | 建立带模型/维度版本的新投影，经验证切换；禁止不同空间混查。 |
| 新 Prompt / Domain 规则 | 创建新 GenerationRun 与候选修订；评测后切换，不静默重算全部用户历史。 |

重建搜索投影使用已保存语义结果，不调用 LLM。重新解释历史是另一项显式、有成本且受当前授权限制的操作。

## 7. “生长”与半衰期的收敛实现

首版只证明四种能力：证据积累、情境区分、显式纠正、随时间休眠。无须先实现开放式人格推理。

分开记录三个轴：审核状态 candidate/approved/rejected；生命周期 active/dormant/superseded；处理状态 pending/running/ready/failed。deleted 由删除屏障控制。reactivated 是一次事件，而非永久状态；stable 是稳定性估计，不与上述状态混用。

同时记录事件发生时间、系统记录时间及适用区间，允许未知时间；先支持当前查询和基本历史查询，完整双时态历史重建后置。

证据强度、当前适用性和召回激活度不共用一个 confidence。起步可采用带版本的固定衰减规则，但参数是工程假设，不是经验证的人类记忆规律。自适应半衰期只有在固定策略基线上证明收益后才上线。

强化来自独立用户证据或明确确认。同一事件重试、assistant 复述、检索命中以及系统重复使用都不自动加强可信度，避免自我强化。休眠减少默认召回，不能替代数据删除；无再次提及也不自动意味着曾经的事实错误。显式偏好可不做普通衰减，仍服从修改、撤销、保留和用途限制。

## 8. 技术选型：默认方案与验证项

需要进一步选型，但范围限于首版。以下为提案，不表示已完成兼容或性能验证。

| 项目 | 默认方案 | 理由与冻结条件 |
| --- | --- | --- |
| 语言与数据校验 | Python；保留现有 3.11+ 方向，Pydantic | 延续仓库生态；在 CI 和部署镜像确定支持版本。 |
| 权威存储 | PostgreSQL，SQLAlchemy，Alembic | 统一事务、任务、关系和迁移；验证目标部署提供的版本与扩展。 |
| 部署 | 一个代码包；API/SDK 与 worker 共用代码、独立进程 | 清楚的请求与后台资源边界；首版单区域，实例数量由压测决定。 |
| 工作队列 | PostgreSQL 持久任务表 | 降低运维组件数；用故障测试验证并发领取、租约和重放。 |
| HTTP | 预留 FastAPI 适配位置，按独立服务接入需要交付 | 首版推荐 SDK 路径；HTTP 暴露前必须有调用身份与权限映射。 |
| 搜索 | M1 按类型、情境和时间读取有效视图；M2 验证中文词法检索，embedding 仅作可选对照 | pgvector 不作为基础安装要求；普通 PG 全文检索不能直接等同于中文 BM25。语义通道是否启用由留出集效果与成本决定。 |
| 模型 | M2 一个提取 provider，窄接口封装；embedding provider 按实验需要增加 | 模型名、成本、数据去向在用合成数据进行的小样评测后冻结；不实现通用路由平台。 |
| 观测与测试 | 结构化内容脱敏日志、指标、trace ID；pytest、真实 PostgreSQL 集成测试 | 能定位积压、失败和成本；不以 SQLite 测试替代 PostgreSQL 一致性测试。 |

本阶段不承诺多后端。SQLite 不是首版生产后端；独立向量库、图数据库和专用队列仅在现有方案无法满足已测负载时讨论。

模型选型前确认中文抽取、指令注入抵抗、响应结构、失败率、延迟、费用和允许的数据目的地。部署前还必须记录备份恢复方式、RPO/RTO、原文保留期与负责人。具体数字依真实业务预算确定，当前不虚构 SLA。

PostgreSQL 已确认为权威存储，不等于已确认托管厂商、部署地区或所有数据流只在数据库内部。若启用外部提取或 embedding 模型，输入会经过对应供应商；真实数据首次外发前须由业务明确允许的处理目的地。未确认时只用规则或合成数据验证。

### 8.1 信任制用量护栏

面向已授权的正常请求默认放行，达到测试确定的异常频率、资源压力或预算门槛后才限制，符合“常开闸机”的产品意图。此机制只控制资源与经济成本；身份隔离、授权、删除屏障和输入大小上限始终检查。

Mirror 不建设计费系统。若业务将付费或套餐状态用于访问许可，应转换为业务授权或预算配置；Mirror 不接收支付凭据、不判定收费规则。不因正常的高频对话推断用户恶意。

| 用量状态 | 行为 |
| --- | --- |
| open | 授权成立且资源正常，执行正常调用并记录消耗。 |
| constrained | 超过软阈值或队列压力升高，合并可合并的后台工作、降低整合频率或延后执行；保留原始独立证据。返回明确处理状态。 |
| paused | 达到硬预算/并发/积压上限，暂停新的昂贵模型任务；队列无容量则拒绝接收新事件，不能 accepted 后丢弃。允许范围内继续读取已有记忆。 |
| recovery | 冷却期或预算窗口重置后少量试探，负载持续低于恢复阈值再恢复；也允许业务显式调整配置。 |

费用上限不阻断授权撤销、删除或错误记忆的同步停用；为这些操作保留独立处理能力，并防止新模型任务挤占。暂停整合期间纠正可先停用旧理解，新理解显示 pending。

首版只维护 app/tenant 总护栏及 subject 公平性护栏。参数包括窗口内事件数、模型调用/token 用量、并发上限、最大队列长度/年龄、单事件大小、软硬费用阈值和恢复条件。不按用户数简单推导负载。金额是由版本化模型单价计算的估算，不能当作供应商最终账单；硬安全边界还应有调用/token 上限。

提交模型调用前原子预留预算和并发名额，完成后结算；计入重试及在途请求，避免多个 worker 同时看到余额而超支。调用状态不明时不能立即释放所有预留并无限重试。护栏计数不能仅存在进程内，服务重启不得清空窗口消耗。

测试使用正常对话、长消息、突发流量、单用户高频、模型限流/超时和 worker 重启负载。记录每千条事件成本、每活跃用户窗口成本、调用/token 分布、recall p95、队列等待时间及限流误触发率。先测正常区间，再压测容量边界，以留有余量的参数生成带版本的默认 profile；真实值由测试填入，不在 RFC 中猜测金额或次数。

容量逐步增加 worker 和数据库资源，并在各档负载重跑测量。门槛由业务动态调整且留有变更记录，自动恢复不等于自动提高预算上限。未来仅在实测瓶颈明确时引入专用队列或独立搜索服务。

### 8.2 动态成本效率工作点

不要求产品负责人事先猜测 QPS、token 或调用次数门槛，这些由测试产出。“最高性价比”暂定义为：满足既定记忆质量、错误/陈旧注入限制和交互延迟要求的配置中，选择成本较低且容量有余量的一档。它是给定模型、负载和测试集下的工作点，不承诺一个永久全局最优值，也不能用少记、不召回获得表面低成本。

先离线比较处理频率、批量大小、召回预算和候选模型等少量配置；内部试点监测成本、积压和失败率，质量用固定留出集及人工抽查确认。积累足够样本后提出 profile 更新，在测试环境验证、保留回退版本；首版不建设自主在线优化器。压力控制使用冷却和不同进入/恢复阈值，避免频繁开关。

质量底线、实测容量上限与可承受损失是不同约束。动态工作点不能代替测试总预算或失控停机上限；后者由运行方在付费实验前设置。此上限是实验保险，不是要求用户预测最佳性能参数。未有预算时可以完成确定性内核、合成样例和不调用付费模型的测试，不能据“动态调整”开展无上限付费探索。

## 10. 验证标准与发布门槛

测试以外部可观察行为为中心；不是每个对象都需要机械单元测试。

| 契约组 | 最小验收场景 |
| --- | --- |
| 身份和隔离 | 伪造 subject、跨 tenant、越权历史查询、未知用途都被拒绝；合法跨会话召回成立。 |
| 证据与模型 | 错角色归因、缺失/跨主体证据、非法 schema、原文指令注入均不能成为批准记忆。 |
| 幂等与并发 | 同事件重复请求、重复投递、崩溃重试不重复强化；两个 worker 不覆盖更高版本视图。 |
| 撤销和删除 | 覆盖外发前、模型返回后、提交前的撤销；删除后任务重放、缓存和备份恢复不复活数据。 |
| 授权同步 | 缺失/过期授权拒绝；乱序旧版本不覆盖新版本；延迟/重复通知、运行中撤销可测且有确认边界。 |
| 用量护栏 | 正常请求放行，突发时不突破并发预留；预算用尽可恢复，重启不清空消耗；暂停后不丢已接收事件、不阻断撤销和删除。 |
| 召回语义 | accepted 与 ready 区分；正确处理 empty、pending、timeout；临时偏好不覆盖长期偏好。 |
| 重建与升级 | 删除派生索引后重建；新 embedding/Prompt/schema 版本切换有验证与回退路径。 |

质量评测使用版本化、经授权或合成的中文多会话样例，覆盖偏好复现、作用域变化、纠正、遗忘、拒答与无关记忆。划分开发集和留出集，避免用同一批样例调规则又报告效果。

至少比较“无长期记忆”“原始会话检索”“Mirror 固定生命周期”。随后才比较自适应策略。统一模型、token 预算、数据切分和检索设置；分别记录抽取准确度、召回覆盖、陈旧/冲突注入率、证据可追踪率、成本和延迟。不能用单一端到端回答分数掩盖错误记忆。

在相同数据和返回预算下单独比较“结构化召回”“结构化＋词法”“结构化＋词法＋embedding”。已知类型的偏好直接读取当前视图，开放式经历查询才需要寻找语义候选。仅在 embedding 带来可验证的有效召回增益，且无关/陈旧注入、延迟和成本满足预先约定的门槛时启用。向量副本沿用来源的访问和删除规则，不能视为匿名数据。

发布须通过所有隔离、删除、幂等强制用例，无已知阻断缺陷；这不等于证明所有现实情况绝无故障。业务质量在留出集上达到预先约定目标，关键安全指标不能退化，并完成小范围接入、恢复演练、限额和人工故障处置说明。具体性能/成本目标在首个业务确认后写入发布清单。

| 阶段 | 交付与退出条件 |

| M3：Psych 内部验收 | 信任制护栏与恢复、授权握手/撤销、运维、备份恢复、版本升级及记忆效果通过验收；模拟时间覆盖遗忘与过期，并验证多会话测试。生产接管另行评审。 |
| M4：跨产品验证 | 在笔润智谈等产品以独立 Scope 和数据接入，复跑通用契约与产品质量测试；验证是否能仅新增领域适配而无需改写内核，不迁移 Psych 私人记忆。 |

已确认旧 Mirror 无实际使用人群，旧版退役，新版无须兼容旧 API、配置、schema 或旧记忆数据。不实现旧版适配层、旧数据迁移器及双轨运行；历史代码可通过 Git 历史追溯，新版目录与接口按新契约设计。这里取消的是旧 Mirror，Psych 的现有业务系统不在退役范围内。新版自身后续的 schema migration、版本升级和故障回退仍为生产要求。本次只更新架构决策，尚未执行远程仓库归档、服务关闭或文件删除。
